Chapter 1 — Introduction

1-1.Purpose. This playbook walks you through building, experimenting with, and tearing down the Mini-PaaS platform on AWS: a self-hosted deployment platform (specification LK-MP-PRD-001) where a git push becomes a live, scaled, isolated application — and then, at the end, a zero-cost AWS account again. It is an exercise, not a production service.

1-2.How to use this playbook. Work strictly in order — exercises are sequenced so that everything a step needs already exists. Three habits are mandatory:

  1. Run every CHECKPOINT. A green CHECKPOINT box after a step is not optional ceremony; it is how you find out a silent failure happened now instead of three exercises later.
  2. Never copy an identifier from an example. Anything shaped like vpc-0b9b…, subnet-…, or an ARN with a random suffix was generated for a build that no longer exists. Discover your own with kubectl, terraform, and aws.
  3. Run commands from the repository root (~/linkify/kubernetes-vercel).

1-3.What "experiments" means here. Every exercise ends with a try-a-change block: a deliberate, reversible variation (an instance type, a replica count, an HPA target, a network policy) plus what to observe. That is the actual point of this project — not clicking through a known-good script, but making a change and reading what the platform does.

Warning — real money

From Exercise 1 onward this procedure creates billable AWS resources — roughly $150–216/month while the platform runs, depending on node pricing (Appendix B). The teardown in Exercise 8 returns the account to baseline and is part of the procedure, not an afterthought. Never end a working session without either completing teardown or consciously deciding — out loud, to Aayush — that the platform stays up.

Note — when something breaks

Something will break; that is the nature of the exercise. The debugging sequence is always the same: read the actual error (kubectl describe, events, logs, Terraform plan), locate which layer refused (admission? scheduler? controller? AWS API?), and fix the declaration in git rather than the live object. Appendix A maps the recurring symptoms to their causes.

Chapter 3 — Exercise 1: Infrastructure up

3-1.Objective. Provision the entire cluster — VPC, EKS, Karpenter controller, ECR repositories, IAM — from code, and point kubectl at it. Satisfies REQ-3.1-1 … 3.1-7.

3-2.State backend (once).

cd infra
./bootstrap-state.sh        # creates the S3 bucket + DynamoDB lock table, writes backend.tfvars
Note — us-east-1 quirk

CreateBucket in us-east-1 rejects a LocationConstraint; the script handles this. The dynamodb wait table-exists step is there because create-table returns before the table is ACTIVE — without it, the first plan fails with ResourceNotFoundException on the lock.

3-3.Init, plan, apply — the review gate is the plan.

terraform init -backend-config=backend.tfvars
terraform plan -out=plan.tfplan     # READ this. ~91 resources. It is the review gate.
terraform apply plan.tfplan          # EKS cluster takes 15–25 minutes
Command by command — Exercise 1
./bootstrap-state.sh
One-time. Creates the S3 state bucket (versioned, encrypted) and the DynamoDB lock table, then writes infra/backend.tfvars. Bucket + table are what make multi-operator state safe.
terraform init -backend-config=backend.tfvars
Downloads the AWS/Helm/Kubernetes providers and points Terraform at the remote state backend. -backend-config supplies the bucket/table/region without hardcoding them into the code.
terraform plan -out=plan.tfplan
Reads real AWS, diffs it against the .tf files, prints every change, and saves the plan. This is the review gate — read it before you apply anything.
terraform apply plan.tfplan
Executes the saved plan. This step creates the EKS cluster, so it runs 15–25 minutes and touches ~91 resources.
aws eks update-kubeconfig --region us-east-1 --name mini-paas
Writes a kubeconfig entry so kubectl can reach this cluster, minting short-lived credentials from your SSO session — no static keys.
kubectl get nodes / kubectl get ns
The two sanity reads: are the nodes Ready, and is the cluster still empty of tenants?
Checkpoint 3-A
aws eks update-kubeconfig --region us-east-1 --name mini-paas
kubectl get nodes                 # one bootstrap node, Ready, private IP only
kubectl get ns                    # no app-* namespaces yet
kubectl -n kube-system get pods   # coredns, aws-load-balancer-controller, karpenter running
Anatomy — what terraform apply just did
vpc
VPC, 3 private + 3 public subnets, one NAT gateway (cost), route tables, internet gateway, security groups.
eks
Cluster (no customer KMS key — EKS uses its own; see TM-002 ch. 4), bootstrap node group, addons (coredns, kube-proxy, vpc-cni, ebs-csi).
karpenter
Controller IAM (Pod Identity), node IAM role, interruption SQS queue, controller Helm chart. The NodePool/EC2NodeClass are applied separately (Exercise 2).
iam
ALB controller IRSA role, GitHub Actions OIDC role (ECR push only).
ecr
Five mini-paas/* repositories, immutable tags.
Experiment 1-A — change the node size
# infra/variables.tf → node_instance_type
cd infra && terraform plan -out=plan.tfplan && terraform apply plan.tfplan
kubectl get nodes -o wide

Why this matters: the node pool is the dial that controls both cost and how quickly the autoscaling demo fires (Chapter 8). You are making the platform cheaper or more eager, on purpose.

Chapter 4 — Exercise 2: Pipeline & GitOps bootstrap

4-1.Objective. Install ArgoCD, register the GitOps App-of-Apps, point Karpenter at nodes, and confirm GitHub Actions can assume its AWS role via OIDC. Satisfies REQ-3.2-1 … 3.2-4 and REQ-3.3-1.

4-2.ArgoCD.

helm repo add argo https://argoproj.github.io/argo-helm
helm install argocd argo/argo-cd -n argocd --create-namespace
kubectl -n argocd get pods -w
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d
Command by command — ArgoCD install
helm repo add argo https://argoproj.github.io/argo-helm
Registers the ArgoCD Helm chart repository so Helm knows where to fetch argo/argo-cd from.
helm install argocd argo/argo-cd -n argocd --create-namespace
Renders the chart with defaults and applies it as one tracked release. --create-namespace is what actually makes the argocd namespace.
kubectl -n argocd get pods -w
-w = watch: re-prints the list as it changes, so you see the controller come up live instead of polling.
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d
ArgoCD seeds a random admin password in a Secret on first install. This extracts it and decodes it (base64 -d) so you can log in once.

4-3.Register GitOps. The App-of-Apps deploys everything, in sync-wave order: the Prometheus CRDs (wave 0), Karpenter's NodePool (wave 5), then metrics-server + monitoring + the five tenants (waves 10–15). Because ArgoCD renders Helm charts via helm template (which skips the chart's crds/ directory), the CRDs ship in gitops/crds/ and are applied as raw manifests — server-side — by the crds app.

kubectl apply -f gitops/bootstrap/app-of-apps.yaml
argocd app list    # one parent app (mini-paas-apps); it discovers the child apps in gitops/apps/

4-4.Give Karpenter its node dial. The controller is up (from terraform); the NodePool/EC2NodeClass tell it what nodes look like. The karpenter app (gitops/apps/karpenter.yaml) deploys them automatically — no manual apply (see TM-002 ch. 4 for why they are not in Terraform).

kubectl get nodepools,ec2nodeclasses
Command by command — registering GitOps
kubectl apply -f gitops/bootstrap/app-of-apps.yaml
Tells the cluster "make live state match this file" — the declarative statement. It creates the parent ArgoCD Application, which then discovers the child Applications in gitops/apps/.
argocd app list
The ArgoCD CLI reading the controller's view of Applications — the fastest way to see whether the parent found its children.
karpenter app (gitops/apps/karpenter.yaml)
Deploys the NodePool + EC2NodeClass — the two CRDs that tell Karpenter when to buy nodes and what they look like. Deployed by the App-of-Apps (sync-wave 5), not by hand — they are cluster objects that can only exist after the controller is running.

4-5.CI role secret. The pipeline assumes an IAM role via OIDC. Put the role ARN in GitHub so Actions can assume it:

cd infra && terraform output github_actions_role_arn
# → add as a GitHub Actions secret named AWS_ROLE_ARN on the kubernetes-vercel repo

4-6.Wire the ingress domain (once). The ingress manifests reference __INGRESS_DOMAIN__. After the ALB exists (Exercise 5), replace it across the five ingress files with your wildcard domain — e.g. <alb-dns>.nip.io — and push.

Checkpoint 4-A
kubectl -n argocd get pods              # argocd-server running
argocd app list                          # mini-paas-apps Healthy
kubectl get nodepools                   # default ready
# push an empty commit to any app and watch the run pass:
cd apps/api-node && git commit --allow-empty -m "pipeline smoke test" && git push
gh run watch

Each pipeline stage is visible: build → test → push to ECR (SHA tag) → update gitops manifest → push. If it fails at "assume role", fix infra/oidc.tf — never add static keys.

Chapter 6 — Exercise 4: Multi-tenancy experiments

6-1.Objective. Prove the isolation layer works: quotas reject, limits constrain, network policies block. Satisfies REQ-3.4-1 … 3.4-5.

kubectl get resourcequota -n app-api-node -o yaml
kubectl get limitrange -n app-api-node
kubectl get networkpolicy -n app-api-node
Command by command — reading the isolation layer
kubectl get resourcequota -n app-api-node -o yaml
Shows the namespace's quota as structured YAML — the exact limits the admission controller will enforce.
kubectl run oversized --limits='cpu=2,memory=2Gi' ...
Attempts to create a pod whose limits exceed the LimitRange/ResourceQuota. The admission controller refuses it before it ever becomes a pod.
kubectl describe pod oversized -n app-api-node
Where the rejection reason actually lives — the events. Not the logs.
kubectl exec -n app-api-node deploy/api-node -- wget ...
Runs a command inside a running pod — here, attempting a cross-namespace request to prove the NetworkPolicy blocks it.
Experiment 4-A — push a workload past its quota
kubectl -n app-api-node run oversized --image=busybox --restart=Never \
  --limits='cpu=2,memory=2Gi' --command -- sh -c "sleep 3600"
kubectl describe pod oversized -n app-api-node
kubectl get events -n app-api-node | tail -20

The pod is refused. Read the events, not the logs — quota rejection is diagnosed in kubectl describe, exactly as it is in production.

Experiment 4-B — cross-tenant traffic is blocked
kubectl exec -n app-api-node deploy/api-node -- \
  wget -qO- --timeout=3 http://go-api.app-go-api.svc.cluster.local/ || echo "BLOCKED"

The NetworkPolicy (egress = same-namespace + DNS only) stops it. Same-namespace traffic still works — isolation without breaking your own app.

Caution — namespace deletion is irreversible

Deleting a namespace deletes everything in it with no undo. When you clean up experiments, delete the pods/jobs you created, not the namespace. Verify the target namespace before deleting anything.

Chapter 7 — Exercise 5: Ingress, DNS & TLS verification

7-1.Objective. Confirm host-based routing through the ALB, wildcard DNS, and (optionally) TLS. Satisfies REQ-3.6-1 … 3.6-4.

kubectl get ingress -A
kubectl get svc -n kube-system | grep -i alb
nslookup api.<ingress-domain>
curl -sI https://api.<ingress-domain>/
Checkpoint 7-A

Five host rules exist on one shared ALB (group.name: mini-paas); all five subdomains resolve and return HTTP 200. If DNS is empty, the wildcard record was not pointed at the ALB address — fix the record, not the ingress.

Note — TLS is optional here

With a real domain, cert-manager + Let's Encrypt issues certs (REQ-3.6-3). With the default nip.io/sslip.io wildcard, HTTPS via self-signed/HTTP is acceptable — do not let TLS become the thing that eats a week.

kubectl apply -f apps/loadgen/job.yaml

Command by command — the scaling lab
kubectl apply -f apps/loadgen/job.yaml
Creates a Job running 8 parallel wget loops against api-node's CPU-burn endpoint, hammering the in-cluster Service name.
kubectl get hpa -n app-api-node -w
Watches the HPA — you'll see the TARGETS column cross the 50% line and REPLICAS climb.
kubectl get nodes -w
Watches node count — the moment pods stop fitting on existing nodes, Karpenter adds one here.
Checkpoint 8-A — the scaling proof

Pod level: api-node replicas climb past 1 as its CPU crosses the 50% target (HPA). Node level: a new Karpenter-provisioned node appears as the pods no longer fit. On Grafana, both appear in real time. Stop the load (kubectl delete job loadgen) and watch both autoscalers consolidate back to baseline.

Experiment 6-A — retune the HPA and feel the difference
# gitops/manifests/api-node/hpa.yaml → averageUtilization: 30, maxReplicas: 8
git commit -am "api-node: HPA target 30%" && git push
# rerun the load; the scale-up should trigger faster and climb higher

The target percentage is the sensitivity dial. Try 30%, then 70%, and compare how quickly and how far the platform scales. This is REQ-3.7-5 — you can now explain a scale event from metrics, not just watch one.

Warning — Karpenter that never scales down

A load test left running keeps the cluster scaled out and the bill climbing. Every scaling session ends with load stopped and both HPA and Karpenter back at baseline. Never end a session mid-load.

Chapter 9 — Exercise 7: Rollback experiment

9-1.Objective. Deliberately ship a broken release, watch it fail, and recover with git — the undo button. Satisfies REQ-3.9-1 … 3.9-3.

9-2.Break it.

# apps/api-node → point the image at a tag that does not exist
#   (the CI pipeline writes the image; simulate by editing the gitops deployment image directly)
# e.g. gitops/manifests/api-node/deployment.yaml → image: <registry>/mini-paas/api-node:does-not-exist
git commit -am "api-node: (deliberately broken image)" && git push
argocd app sync app-api-node
kubectl get pods -n app-api-node   # ImagePullBackOff — read the events

9-3.Fix it with git.

git revert HEAD --no-edit
git push
argocd app sync app-api-node
kubectl get pods -n app-api-node -w
Checkpoint 9-A

The application returns to healthy within 10 minutes of the revert. The image tag, git history, and ArgoCD sync all tell the same story — explain that story in one paragraph (this is also the final step of the end-to-end demonstration in PRD Appendix D).

Chapter 10 — Exercise 8: Teardown

10-1.Objective. Destroy everything cleanly, in the order that prevents ArgoCD from fighting the destroy. This org has no production projects, so teardown is allowed to take everything down. Satisfies REQ-3.10-1 … 3.10-4.

./scripts/teardown.sh

10-2.What the script does (six phases).

  1. Stops GitOps: deletes the App-of-Apps, uninstalls ArgoCD, removes the argocd namespace.
  2. Deletes every non-system namespace (kube-system, kube-public, kube-node-lease, default survive) — catches any experiment leftovers.
  3. terraform destroy -auto-approve — the bill killer.
  4. Residual sweep: terminates all EC2 instances, deletes available EBS volumes, releases unassociated EIPs, deletes ALB/NLB, ECR repos, SQS queues.
  5. Removes the S3 state bucket + DynamoDB lock table (read from backend.tfvars).
  6. Done — account back to ~$0.
Note — what teardown will NOT touch

IAM Identity Center / SSO permission sets and the reserved SSO roles. That is how everyone logs in — removing them would lock you out of the account. Everything an experiment could have created is fair game.

Warning — the cost alarm is not a suggestion

If the budget alarm fires, stop the load test and scale down or destroy. This is an exercise; a surprise AWS bill is the one failure that cannot be rolled back.
