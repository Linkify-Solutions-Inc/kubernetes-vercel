Chapter 1 — Introduction

1-1.Purpose. This playbook walks you through building, experimenting with, and tearing down the Mini-PaaS platform on AWS: a self-hosted deployment platform (specification LK-MP-PRD-001) where a git push becomes a live, scaled, isolated application — and then, at the end, a zero-cost AWS account again. It is an exercise, not a production service.

1-2.How to use this playbook. Work strictly in order — exercises are sequenced so that everything a step needs already exists. Three habits are mandatory:

  1. Run every CHECKPOINT. A green CHECKPOINT box after a step is not optional ceremony; it is how you find out a silent failure happened now instead of three exercises later. If a checkpoint's expected output doesn't match, stop and consult Appendix A.
  2. Never copy an identifier from an example. Anything shaped like vpc-0b9b…, subnet-…, <account-id>, or an ARN with a random suffix was generated for a build that does not exist yet. Discover your own with kubectl, terraform, and aws.
  3. Run commands from the repository root (~/linkify/kubernetes-vercel in this playbook). Relative paths like -f infra/… resolve from there.

1-3.What "experiments" means here. Every exercise ends with a try-a-change block: a deliberate, reversible variation (an instance type, a replica count, an HPA target, a network policy) plus what to observe. That is the actual point of this project — not clicking through a known-good script, but making a change and reading what the platform does.

Warning — real money

From Exercise 1 onward this procedure creates billable AWS resources — roughly $150–210/month while the platform runs, depending on node pricing (Appendix B breaks it down). The teardown in Exercise 8 returns the account to baseline and is part of the procedure, not an afterthought. Never end a working session without either completing teardown or consciously deciding — out loud, to Aayush — that the platform stays up overnight.

Note — when something breaks

Something will break; that is the nature of the exercise. The debugging sequence is always the same: read the actual error (kubectl describe, events, logs, Terraform plan), locate which layer refused (admission? scheduler? controller? AWS API?), and fix the declaration in git rather than the live object. Appendix A maps the recurring symptoms to their causes.

Chapter 2 — Prerequisites & workstation

2-1.Tools. Install the AWS CLI v2, Terraform, kubectl, Helm, git, the GitHub CLI (gh), and jq. All from official sources:

# AWS CLI v2
curl -fsSL "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o /tmp/awscliv2.zip
unzip -q /tmp/awscliv2.zip -d /tmp && sudo /tmp/aws/install

# Terraform (current stable)
curl -fsSL "https://releases.hashicorp.com/terraform/1.9.0/terraform_1.9.0_linux_amd64.zip" \
  -o /tmp/tf.zip && unzip -q /tmp/tf.zip -d /tmp && sudo mv /tmp/terraform /usr/local/bin/

# kubectl (current stable)
curl -fsSLO "https://dl.k8s.io/release/$(curl -Ls https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
sudo install -m 0755 kubectl /usr/local/bin/kubectl && rm kubectl

# Helm
curl -fsSL https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash

# git + GitHub CLI + jq
sudo apt-get update && sudo apt-get install -y git jq
(which gh || (curl -fsSL https://cli.github.com/packages/githubcli-archive-keyring.gpg \
  | sudo dd of=/usr/share/keyrings/githubcli-archive-keyring.gpg && echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/githubcli-archive-keyring.gpg] https://cli.github.com/packages stable main" | sudo tee /etc/apt/sources.list.d/github-cli.list >/dev/null && sudo apt-get update && sudo apt-get install -y gh))
Checkpoint 2-A
aws --version          # aws-cli/2.x
terraform version      # v1.9.x
kubectl version --client
helm version --short   # v4.x (v3.15+ acceptable)
git --version && gh --version && jq --version

Every command prints a version. Sign in to AWS and to GitHub before continuing (gh auth login).

Command anatomy — what each tool actually is
aws
A signed-HTTP client for every AWS API. Nothing is magic — every subcommand is a request you could have made with curl and a signature.
terraform
The infrastructure compiler: init fetches providers, plan computes a diff between your code and reality, apply executes it. State lives in S3 (locked by DynamoDB) — it is the source of truth for what you own.
kubectl
The Kubernetes API client. Everything it does is an HTTPS call to the cluster's API server, authenticated via your AWS identity (EKS).
helm
A package manager for Kubernetes: a "chart" is templated YAML plus defaults; install renders it with your values and applies the result as one tracked release.
gh
The GitHub CLI — used here to inspect Actions runs and the pipeline side of the loop.

2-2.Repository.

mkdir -p ~/linkify && cd ~/linkify
git clone https://github.com/Linkify-Solutions-Inc/kubernetes-vercel.git
cd kubernetes-vercel
Note — repository layout

infra/ is Terraform (cluster, VPC, Karpenter, ECR, DNS, IAM). apps/ is the five demo applications plus loadgen. gitops/ is the ArgoCD source of truth (manifests, not kubectl). docs/ holds this manual, the explainer volume, and the PRD.

Chapter 3 — Exercise 1: Infrastructure up

3-1.Objective. Provision the entire cluster — VPC, EKS, Karpenter, ECR repositories, IAM — from code, and point kubectl at it. This satisfies REQ-3.1-1 … 3.1-7.

cd infra
terraform init
terraform plan -out=plan.tfplan
terraform apply plan.tfplan
aws eks update-kubeconfig --region us-east-1 --name mini-paas
kubectl get nodes
kubectl get ns
Checkpoint 3-A
kubectl get nodes      # every node Ready, private-IP only (no public IPs)
kubectl get ns         # system namespaces only — NO app-* namespaces yet
aws ecr describe-repositories --region us-east-1  # five mini-paas/* repos exist

If plan or apply fails: read the error, fix the declaration in infra/, re-apply. Do not "fix" state by hand.

Anatomy — what terraform apply just did
init
Downloads the AWS provider and configures the S3/DynamoDB state backend. No cloud changes.
plan
Diffs your desired state (the .tf files) against real AWS and prints the full change set. This is your review gate — read it.
apply
Executes the plan. The EKS module creates the cluster, and Karpenter becomes the thing that creates nodes on demand.
IRSA
Every pod identity is an IAM role bound to a Kubernetes service account — no access keys inside the cluster. If a step ever tells you to paste an ARN into a secret, the design is wrong.
Experiment 1-A — change the node size
# in infra/karpenter.tf, set instance-type: t3.large
cd infra && terraform apply
kubectl get nodes -o wide
# observe the new node's capacity
# set it back to t3.medium and re-apply

Why this matters: the node pool is the one dial that controls both cost and how quickly the autoscaling demo fires (Chapter 8). You are making the platform cheaper or more eager, on purpose.

Chapter 4 — Exercise 2: Pipeline & GitOps bootstrap

4-1.Objective. Stand up ArgoCD, verify GitHub Actions authenticates to AWS via OIDC (no keys anywhere), and confirm the CI → GitOps loop end to end. Satisfies REQ-3.2-1 … 3.2-4 and REQ-3.3-1.

helm repo add argo https://argoproj.github.io/argo-helm
helm install argocd argo/argo-cd -n argocd --create-namespace
kubectl -n argocd get pods -w
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d
Checkpoint 4-A
kubectl -n argocd get pods        # argocd-server running
kubectl -n argocd port-forward svc/argocd-server 8080:80
# browser: https://localhost:8080  (admin + the password printed above)

4-2.OIDC check. The GitHub Actions role was created by Terraform. Make a trivial push to any app and watch the pipeline assume the role — with no stored credentials.

cd apps/api-node && git commit --allow-empty -m "pipeline smoke test" && git push
gh run watch
Checkpoint 4-B

The run passes and each stage is visible: build → test → push to ECR (SHA tag) → update gitops manifest → push. If it fails at "assume role", the OIDC trust policy in Terraform is wrong — fix infra/oidc.tf, not the workflow.

Anatomy — the GitOps loop
GitHub Actions
Builds images and writes the desired state. It never touches the cluster directly.
ECR
The image registry. Every push is tagged immutably with its commit SHA — the tag is the identity.
gitops/ repo
The single source of truth for cluster workloads. Changing a manifest here is the "deploy".
ArgoCD
The controller that reconciles: it polls git, compares to the live cluster, and syncs the difference. It is the deployment engine.

Chapter 6 — Exercise 4: Multi-tenancy experiments

6-1.Objective. Prove the isolation layer works: quotas reject, limits constrain, network policies block. Satisfies REQ-3.4-1 … 3.4-5.

kubectl get resourcequota -n app-api-node -o yaml
kubectl get limitrange -n app-api-node
kubectl get networkpolicy -n app-api-node
Experiment 4-A — push a workload past its quota
kubectl -n app-api-node run oversized --image=busybox --restart=Never \
  --limits='cpu=2,memory=2Gi' --command -- sh -c "sleep 3600"
kubectl describe pod oversized -n app-api-node
kubectl get events -n app-api-node | tail -20

The pod is refused. Read the events, not the logs — quota rejection is diagnosed in kubectl describe, exactly as it is in production.

Experiment 4-B — cross-tenant traffic is blocked
# from inside api-node's pod, try to reach go-api in ITS namespace
kubectl exec -n app-api-node deploy/api-node -- \
  wget -qO- --timeout=3 http://go-api.app-go-api.svc.cluster.local/ || echo "BLOCKED"

The NetworkPolicy (default-deny, allow same-namespace, allow ingress) stops it. Same-namespace traffic still works — isolation without breaking your own app.

Caution — namespace deletion is irreversible

Deleting a namespace deletes everything in it with no undo. When you clean up experiments, delete the pods/jobs you created, not the namespace. Verify the target namespace before deleting anything.

Chapter 7 — Exercise 5: Ingress, DNS & TLS verification

7-1.Objective. Confirm host-based routing through the ALB, wildcard DNS, and (optionally) TLS. Satisfies REQ-3.6-1 … 3.6-4.

kubectl get ingress -A
kubectl get svc -n kube-system | grep -i alb
nslookup api.<ingress-domain>
curl -sI https://api.<ingress-domain>/
Checkpoint 5-A

Five host rules exist in the ingress controller; all five subdomains resolve to the ALB and return HTTP 200/301. If DNS is empty, the wildcard record (nip.io/sslip.io) was not pointed at the ALB address — fix the record, not the ingress.

Note — TLS is optional here

With a real domain, cert-manager + Let's Encrypt issues certs (REQ-3.6-3). With the default nip.io/sslip.io wildcard, HTTPS via self-signed/HTTP is acceptable for the exercise — do not let TLS become the thing that eats a week.

Chapter 8 — Exercise 6: Autoscaling & observability lab

8-1.Objective. The heart of the project: under generated load, HPA scales pods and Karpenter scales nodes — and you watch both happen on a Grafana dashboard. Satisfies REQ-3.7-1 … 3.7-5 and REQ-3.8-1 … 3.8-4.

8-2.Bring up the metrics stack.

helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm install kube-prom prometheus-community/kube-prometheus-stack -n monitoring --create-namespace
kubectl -n monitoring get pods
kubectl -n monitoring port-forward svc/kube-prom-grafana 3000:80
# browser: http://localhost:3000  (admin / admin)

8-3.Baseline.

kubectl get hpa -A
kubectl get nodes

8-4.Drive load at api-node.

kubectl apply -f apps/loadgen/job.yaml
kubectl get hpa -n app-api-node -w
# in another terminal:
kubectl get nodes -w
Checkpoint 8-A — the scaling proof

Pod level: api-node replicas climb past 1 as its CPU crosses the 50% target (HPA). Node level: a new Karpenter-provisioned node appears as the pods no longer fit. On Grafana, both appear in real time. Stop the load (kubectl delete job loadgen) and watch both autoscalers consolidate back to baseline.

Experiment 6-A — retune the HPA and feel the difference
# in gitops/apps/api-node/hpa.yaml: targetAverageUtilization: 30, min 1, max 8
git commit -am "api-node: HPA target 30%" && git push
# rerun the load; the scale-up should trigger faster and climb higher

The target percentage is the sensitivity dial. Try 30%, then 70%, and compare how quickly and how far the platform scales. This is REQ-3.7-5 — you can now explain a scale event from metrics, not just watch one.

Warning — Karpenter that never scales down

A load test left running keeps the cluster scaled out and the bill climbing. Every scaling session ends with load stopped and both HPA and Karpenter back at baseline. Never end a session mid-load.

Chapter 9 — Exercise 7: Rollback experiment

9-1.Objective. Deliberately ship a broken release, watch it fail, and recover with git — the undo button. Satisfies REQ-3.9-1 … 3.9-3.

9-2.Break it.

# in apps/api-node/... point the image tag at a tag that does not exist
# e.g. <account-id>.dkr.ecr.us-east-1.amazonaws.com/api-node:does-not-exist
git commit -am "api-node: (deliberately broken image)" && git push
argocd app sync app-api-node
kubectl get pods -n app-api-node   # ImagePullBackOff — read the events

9-3.Fix it with git.

git revert HEAD --no-edit
git push
argocd app sync app-api-node
kubectl get pods -n app-api-node -w
Checkpoint 9-A

The application returns to healthy within 10 minutes of the revert. The image tag, git history, and ArgoCD sync all tell the same story — explain that story in one paragraph (this is also the final step of the end-to-end demonstration in PRD Appendix D).

Chapter 10 — Exercise 8: Teardown

10-1.Objective. Destroy everything cleanly, in the order that prevents ArgoCD from fighting the destroy. Satisfies REQ-3.10-1 … 3.10-4.

# 1. stop the reconciliation (ArgoCD must not recreate what Terraform deletes)
kubectl delete -f gitops/bootstrap/app-of-apps.yaml
helm uninstall argocd -n argocd

# 2. remove namespaces and workloads
kubectl delete ns monitoring

# 3. destroy the infrastructure
cd infra && terraform destroy
Checkpoint 10-A — the clean-slate proof
aws ec2 describe-instances --region us-east-1 \
  --filters "Name=tag:kubernetes.io/cluster/mini-paas,Values=owned" \
  | jq '.Reservations | length'     # 0
aws ecr describe-repositories --region us-east-1 | jq '.repositories | length'  # 0

Warning — the cost alarm is not a suggestion

If the budget alarm fires, stop the load test and scale down or destroy. This is an exercise; a surprise AWS bill is the one failure that cannot be rolled back.
