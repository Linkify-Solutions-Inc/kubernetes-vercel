Chapter 1 — The ideas underneath everything

1-1.Declarative over imperative. You never tell Kubernetes how to do something step by step; you describe the desired state and a controller makes reality match it. kubectl apply -f manifest.yaml says "this is what I want", not "do this, then this, then this". This single inversion — from procedure to desired state — is the biggest mental shift in modern platform work, and GitOps and autoscaling both fall out of it.

1-2.Infrastructure as code, with a ledger. Terraform treats your AWS account as something you describe in files and reconcile. Three words carry all the meaning: state (what you currently own, recorded in S3, locked by DynamoDB), plan (the diff between what you own and what you wrote — the review gate), and apply (making the plan real). Because the state is the source of truth, everything can be destroyed and recreated — which is exactly why this can be a one-month exercise instead of a permanent gamble.

1-3.GitOps is the deployment engine. There is no custom deploy server and no special "engine" code. The engine is a git repository plus a controller that watches it (ArgoCD). To release a new version you change a file in git; ArgoCD diffs the cluster against the desired state and converges. Deleting a pod is not a bug — it is a test, and ArgoCD wins it.

1-4.Two different autoscalers, two different jobs. Pods scale inside a node (HPA, based on CPU utilization of requests); nodes scale inside the account (Karpenter, based on pods that cannot be scheduled). Confusing them is the classic mistake; Chapter 8 exists to keep them straight.

1-5.Tenancy is a platform responsibility. When many things share one cluster, the person running it owns the boundaries: what each tenant may consume (quota, limits) and what each tenant may reach (network policy). That is the entire job of a platform team, compressed into Chapter 7.

Note — ephemeral by design

Every choice in this architecture (code, not clicks; git, not state; a teardown script that takes everything down) exists so the platform can be born, studied, and destroyed in a month. If a component can only be built but not torn down, it does not belong in the exercise.

Chapter 2 — System architecture & the life of a deployment

2-1.The path from a commit to a live URL. Follow one change through the whole system — this is the picture the project exists to make you hold in your head:

  1. You push a change to an app in GitHub. This is the only human action in the loop.
  2. GitHub Actions builds the container image and runs a minimal check. It authenticates to AWS by federation (OIDC) — trusted temporarily, with no stored keys.
  3. The image lands in ECR under an immutable tag: the commit SHA. The tag is the version's identity for life.
  4. Actions updates the manifest in gitops/manifests/<app>/deployment.yaml — the desired state now points at the new tag.
  5. ArgoCD notices the drift between the gitops repo and the live cluster, and syncs: it applies the manifest, creating or updating the namespace, quota, deployment, service, ingress, and HPA for that app.
  6. The scheduler places the pods on nodes. If no node has room, Karpenter provisions one (via its NodePool/EC2NodeClass).
  7. The ingress controller routes <app>.<domain> through the ALB to the app's Service, which load-balances to the pods.
  8. Prometheus scrapes metrics; if the app's CPU crosses the HPA target, replicas grow — and if pods no longer fit, Karpenter adds a node. Grafana shows all of it.

Chapter 3 — How everything connects (the deep read)

3-1.Chapters 1 and 2 give the path; this chapter gives the wiring — the concrete names, ports, and flows that actually connect one component to another. There are five flows that matter, and each one is traceable through the code in Chapter 4.

3-2. The traffic flow (north-south)

3-2.1.A client hits https://api.<ingress-domain>/work?ms=2000.

client ──HTTPS──▶ ALB (internet-facing, group "mini-paas")
   │  host: api.<domain>  →  ingress rule  →  Service: api-node (app-api-node:80)
   │                                                            │ targetPort: http (3000)
   │                                                            ▼
   │                                           Pod: api-node (containerPort 3000)
   │                                              │
   │                                              ▼ (in-cluster, no DNS/HTTP)
   │                                        POST /work → busy loop → { burned, pid }
   └─────────────────── JSON ────────────────────┘

3-2.2.The Service is the stable name. Everything else (the ALB target, the pod IP) can change; api-node.app-api-node.svc.cluster.local does not. That is why the load generator and cross-tenant experiments use the service name, not a pod IP.

3-3. The state flow (GitOps)

3-3.1.The cluster's desired state lives in gitops/. ArgoCD polls the repository, computes the diff against the live cluster, and converges. The arrows:

gitops/apps/app-of-apps.yaml ──▶ mini-paas-apps (parent Application)
     │  path: gitops/apps
     ▼
gitops/apps/api-node.yaml ──▶ Application "api-node" (child)
     │  source path: gitops/manifests/api-node
     ▼
namespace app-api-node + quota + limits + networkpolicy
     + deployment + service + ingress + hpa     ──▶ applied by ArgoCD sync

3-3.2.Every object a tenant owns is in gitops/manifests/<app>/. There is no other write path into these namespaces — the pipeline writes the image tag, ArgoCD does the rest. If the cluster drifts (someone runs a raw kubectl), self-heal pulls it back.

3-4. The permission flow (who may do what)

3-4.1.There are no long-lived AWS keys anywhere: not in git, not in the cluster. Every principal gets a short-lived credential via federation. This is the single most important security property of the platform, and it is why the prior project's ARN-copying failure mode cannot recur.

3-5. The scaling flow

loadgen (8 parallel wget loops)
   │  GET /work?ms=1500  (over the in-cluster Service)
   ▼
api-node pod: CPU pegged → kubelet reports metrics → metrics-server
   ▼
HPA reads utilization = currentCPU / request(50m)  →  exceeds 50% target
   ▼
HPA writes replicas: N  →  Deployment controller creates pods
   ▼
scheduler: no node fits → pending pods
   ▼
Karpenter: NodePool "default" + EC2NodeClass "default" → buys a t3.medium
   ▼
kubectl get nodes -w shows the new node; Grafana shows it all

3-6. The observability flow

3-6.1.kube-prometheus-stack deploys Prometheus (scraping) + Grafana (dashboards) + node-exporter (node metrics) + kube-state-metrics (object metrics). Prometheus scrapes /metrics from kubelet, node-exporter, and the HPA/metrics path. Grafana renders node CPU, pod CPU, and HPA behavior. The load test and the dashboards are two views of the same number.

3-7. The cost flow

3-7.1.Every billable thing traces to a terraform resource or a Karpenter-provisioned node. The control plane is flat (~$73/mo); nodes, NAT, and the ALB scale with usage. Teardown (Chapter 10 of TM-001) is the reverse of this flow: stop GitOps, destroy namespaces, terraform destroy, then a residual sweep for anything an experiment created outside Terraform.

4-1. infra/main.tf — the VPC, the cluster, the ALB controller

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.0"

  name = local.name
  cidr = var.vpc_cidr

  azs             = local.azs
  private_subnets = [for k, _ in local.azs : cidrsubnet(var.vpc_cidr, 4, k)]
  public_subnets  = [for k, _ in local.azs : cidrsubnet(var.vpc_cidr, 8, k + 48)]

  enable_nat_gateway     = true
  single_nat_gateway     = true   # cost: one NAT for the exercise
  one_nat_gateway_per_az = false
  enable_vpn_gateway     = false

  private_subnet_tags = {
    "karpenter.sh/discovery" = local.name   # Karpenter finds private subnets by tag
  }
  tags = local.tags
}

module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "~> 21.0"

  name                   = local.name
  kubernetes_version     = var.cluster_version
  endpoint_public_access = true

  # Whoever runs `terraform apply` becomes a cluster admin (kubectl access).
  enable_cluster_creator_admin_permissions = true

  # No customer KMS key — EKS uses its own AWS-managed key. Keeps the IAM
  # surface small enough for the StreamingDeploy permission set AND keeps
  # teardown zero-cost (KMS keys linger 7 days and cost $1/mo).
  create_kms_key    = false
  encryption_config = null

  # before_compute: the addons a node needs to become READY (coredns,
  # kube-proxy, vpc-cni) install BEFORE the node group. Otherwise EKS holds the
  # node group in CREATING because the node can't go Ready without the CNI.
  addons = {
    coredns            = { before_compute = true }
    kube-proxy         = { before_compute = true }
    vpc-cni            = { before_compute = true }
    aws-ebs-csi-driver = {}
  }

  vpc_id     = module.vpc.vpc_id
  subnet_ids = module.vpc.private_subnets

  enable_irsa = true

  eks_managed_node_groups = {
    bootstrap = {
      desired_size   = var.node_desired_size
      min_size       = var.node_min_size
      max_size       = var.node_max_size
      instance_types = [var.node_instance_type]
      labels = {
        role                      = "bootstrap"
        "karpenter.sh/controller" = "true"   # Karpenter runs on a node it does NOT manage
      }
      tags = merge(local.tags, {
        "karpenter.sh/discovery" = local.name
      })
    }
  }
  tags = local.tags
}

# ALB controller — the bridge between K8s Ingress and a real ALB.

4-4. .github/workflows/ci.yml — the release side

name: ci
on:
  push: { branches: [main], paths: ["apps/**"] }
  workflow_dispatch:

permissions:
  id-token: write    # OIDC federation to AWS — no static keys anywhere
  contents: write    # to commit the gitops image promotion

env: { AWS_REGION: us-east-1 }

jobs:
  changes:            # which apps changed in this push?
    outputs: { apps: ${{ steps.detect.outputs.apps }} }
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 2 }
      - id: detect
        run: |
          APPS=$(git diff --name-only HEAD^ HEAD -- apps/ 2>/dev/null \
            | sed -n 's|^apps/\([^/]*\)/.*|\1|p' | sort -u \
            | grep -E '^(api-node|web-node|worker-node|py-api|go-api)$' \
            | jq -R -s -c 'split("\n") | map(select(length>0))')
          if [ -z "$APPS" ] || [ "$APPS" = "null" ]; then APPS='[]'; fi
          echo "apps=$APPS" >> "$GITHUB_OUTPUT"

  build:
    needs: changes
    if: needs.changes.outputs.apps != '[]'
    strategy:
      max-parallel: 1        # the gitops push must not race
      matrix: { app: ${{ fromJson(needs.changes.outputs.apps) }} }
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: ${{ env.AWS_REGION }}
      - name: Compute image reference
        id: img
        run: |
          ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
          echo "image=$ACCOUNT.dkr.ecr.${{ env.AWS_REGION }}.amazonaws.com/mini-paas/${{ matrix.app }}:${{ github.sha }}" \
            >> "$GITHUB_OUTPUT"
      - name: Login to ECR
        run: |
          aws ecr get-login-password --region ${{ env.AWS_REGION }} \
            | docker login --username AWS --password-stdin \
              ${{ steps.img.outputs.image }} 2>/dev/null || true
      - name: Minimal check
        working-directory: apps/${{ matrix.app }}
        run: |
          case "${{ matrix.app }}" in
            api-node|web-node|worker-node)
              [ -f package-lock.json ] && npm ci || npm install --no-audit --no-fund
              npm run typecheck ;;
            py-api) python -m py_compile main.py ;;
            go-api) go vet ./... ;;
          esac
      - name: Build image
        run: docker build -f apps/${{ matrix.app }}/Dockerfile \
              -t ${{ steps.img.outputs.image }} apps/${{ matrix.app }}
      - name: Push image (immutable SHA tag)
        run: docker push ${{ steps.img.outputs.image }}
      - name: Promote image in gitops (ArgoCD will reconcile)
        run: |
          IMAGE="${{ steps.img.outputs.image }}"
          sed -i -E "s|^[[:space:]]*image:.*|          image: ${IMAGE}|" \
            gitops/manifests/${{ matrix.app }}/deployment.yaml
          git config user.name "ci-bot" && git config user.email "ci-bot@users.noreply.github.com"
          git add gitops/manifests/${{ matrix.app }}/deployment.yaml
          git commit -m "chore(${{ matrix.app }}): promote image ${GITHUB_SHA}"
          git push

            limits:   { cpu: 250m, memory: 256Mi }
          readinessProbe: { httpGet: { path: /healthz, port: http }, initialDelaySeconds: 5 }
          livenessProbe:  { httpGet: { path: /healthz, port: http }, initialDelaySeconds: 15 }
# hpa.yaml — the pod dial (50% of the 50m REQUEST; modest load trips it fast)
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: api-node, namespace: app-api-node }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api-node }
  minReplicas: 1
  maxReplicas: 8
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 50 }
# networkpolicy.yaml — the fence (ingress open for the ALB; egress locked down)
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny, namespace: app-api-node }
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
  ingress:
    - {}                     # ALB target traffic arrives from outside the pod network
  egress:
    - to: [{ podSelector: {} }]     # same namespace only
    - to:                            # + DNS to CoreDNS (kube-system)
        - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } }
      ports: [{ protocol: UDP, port: 53 }, { protocol: TCP, port: 53 }]

4-6. apps/api-node/src/index.ts — the scaling demo's business logic

import express, { Request, Response } from "express";

const app = express();
const PORT = parseInt(process.env.PORT || "3000", 10);

app.get("/", (_req: Request, res: Response) => {
  res.json({ app: "api-node", message: "Mini-PaaS demo API" });
});

app.get("/healthz", (_req: Request, res: Response) => {
  res.json({ status: "ok" });
});

// CPU burn for the autoscaling demo. `ms` controls how long each request pegs a
// CPU core. A busy loop on purpose, so the CPU metric is real.
app.get("/work", (req: Request, res: Response) => {
  const ms = Math.min(parseInt(String(req.query.ms || "2000"), 10) || 2000, 10000);
  const end = Date.now() + ms;
  while (Date.now() < end) { /* busy loop */ }
  res.json({ app: "api-node", burned: ms, pid: process.pid });
});

app.listen(PORT, () => console.log(`api-node listening on :${PORT}`));

4-6.1.Note pid in the response: hit the URL across several replicas and each response names a different process — the cheapest possible proof that HPA actually scaled you out.

Chapter 6 — The components, one by one

Component anatomy
Amazon EKS
The managed control plane. AWS runs the API server and etcd; you pay a flat hourly rate and operate only the worker nodes. Stock Kubernetes, not a fork.
Karpenter
The node autoscaler. Watches for unschedulable pods, buys the cheapest instance that fits, consolidates idle nodes away. The "machine dial".
ArgoCD
The GitOps controller and therefore the deployment engine. Declarative, self-healing, prunes anything git removed. Its "Application" is the unit of deployment — one per tenant.
AWS Load Balancer Controller
Turns a Kubernetes Ingress object into a real ALB and wires the target group to your Services. The bridge between Kubernetes routing and AWS networking.
kube-prometheus-stack
A Helm chart bundling Prometheus (scrape + storage), Grafana (dashboards), node-exporter, kube-state-metrics. One command; the whole observability story.
IRSA
IAM Roles for Service Accounts: a ServiceAccount maps to an IAM role; pods assume it via projected credentials. No keys in the cluster.
EKS Pod Identity
The newer identity path used by the Karpenter controller — an EKS-level association between a service account and an IAM role, simpler than IRSA's trust-policy plumbing.
GitHub OIDC
The CI job presents a signed token to AWS; AWS verifies it and mints short-lived credentials. Trusted for minutes per run instead of holding keys forever.
Terraform state
S3 bucket (state) + DynamoDB (lock). The ledger that makes plan/apply/destroy possible — and the thing that makes the whole project disposable.

Chapter 7 — Multi-tenancy & isolation explained

7-1.A platform lets many things share one cluster without hurting each other. Three mechanisms compose, and they are deliberately separate:

MechanismAnswersEnforced by
Namespace"What is mine?" — a named boundary for objectsAPI server
ResourceQuota + LimitRange"How much may I take?" — totals per namespace, per-pod boundsAdmission control (rejects before a pod exists)
NetworkPolicy"Who may I talk to?" — default-deny egress, allow same-namespace + DNS, ingress open for the ALBCNI (enforced on the data path)

7-2.Why all three? They answer different questions and fail independently. A namespace without a quota lets one tenant starve the cluster; a quota without a network policy lets one tenant reach another's data. This is exactly how a production platform team thinks — the demo apps are stand-ins for real tenants, but the controls are the real thing.

7-3.Two gotchas worth naming. First, quota rejection surfaces as an event, not a container log — learn to read kubectl get events. Second, ALB target traffic arrives from outside the pod network, so the ingress rule of the NetworkPolicy must stay permissive or the app becomes unreachable; the isolation lesson is taught on the egress side instead (that is why Experiment 4-B blocks outbound cross-tenant calls).

Chapter 8 — Autoscaling economics

8-1.HPA is the pod dial. The HorizontalPodAutoscaler watches CPU utilization of the requests (not the machine's CPU). Because api-node requests 50m CPU and the HPA targets 50%, a modest load spike crosses the threshold quickly — the demo is tuned so the lesson fires with light effort. What HPA cannot do is create more machine.

8-2.Karpenter is the machine dial. When pods exist that no current node can fit, Karpenter buys a node; when nodes sit idle past the consolidation window, it sells them back. t3.medium was chosen because it is the smallest instance where a handful of extra replicas actually forces a new node — the node-scaling lesson cannot even be observed on a bigger instance.

8-3.The cost picture. The EKS control plane costs the same whether nodes are micro or medium — that is why "use a smaller instance to save money" is a trap. Real levers: node count, spot vs on-demand, and NAT choice. The full table is TM-001 Appendix B.

Note — downscaling is half the lesson

Everyone demonstrates scale-up. This project deliberately demonstrates scale-down too: stop the load, and both HPA and Karpenter must consolidate back to baseline. A platform that only grows is a platform that only bills.

Chapter 9 — CI/CD: how code becomes a running platform

9-1.CI (Continuous Integration) is the build side: every push is compiled, checked, and containerized reproducibly. CD (Continuous Delivery) is the release side: the artifact is delivered and promoted. Here, CI lives in GitHub Actions and CD is GitOps — the delivery mechanism is a git commit that a controller reconciles. There is no SSH-into-a-server-and-restart anywhere in the loop.

9-2.Why OIDC and not keys? A stored AWS access key is a permanent credential that outlives its usefulness and leaks. OIDC replaces it with a trust relationship: the pipeline proves its identity to AWS with a short-lived signed token, gets short-lived credentials, and is done. More secure and simpler to operate — no rotation, no "where did the key go".

9-3.Why immutable tags? The image is tagged with its commit SHA, so a running version can always be traced to the exact code that produced it. It also makes rollback trivial: point the manifest at the previous tag (via git revert) and sync. The tag, the git history, and the running pod must always tell the same story — if they ever disagree, someone bypassed the loop.

9-4.As built. The release path described here — and the code in Chapter 4 — is the current, working state of the repository: CI authenticates via OIDC (no keys), the EKS module is v21 with the Karpenter sub-module, the node-critical addons are ordered before_compute, and enable_cluster_creator_admin_permissions = true means the operator who applies owns the cluster. Every command in TM-001 is the procedure that runs against this build.
