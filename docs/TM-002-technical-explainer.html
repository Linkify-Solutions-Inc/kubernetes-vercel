Chapter 1 — The ideas underneath everything

1-1.Declarative over imperative. In this platform you never tell Kubernetes how to do something step by step; you describe the desired state and a controller makes reality match it. kubectl apply -f manifest.yaml says "this is what I want", not "do this, then this, then this". This single inversion of thinking — from procedure to desired state — is the biggest mental shift in modern platform work, and GitOps and autoscaling both fall out of it.

1-2.Infrastructure as code, with a ledger. Terraform treats your AWS account as something you describe in files and reconcile. Three words carry all the meaning: state (what you currently own, recorded in S3), plan (the diff between what you own and what you wrote), apply (making the plan real). Because the state is the source of truth, everything can be destroyed and recreated — which is exactly why this project can be a one-month exercise instead of a permanent gamble.

1-3.GitOps is the deployment engine. The platform has no custom deploy server and no special "engine" code. The engine is a git repository plus a controller that watches it. When you want a new version of an app, you change a file in git; ArgoCD notices, diffs the cluster against the desired state, and converges. Deleting a pod is not a bug — it is a test, and ArgoCD wins it.

1-4.Two different autoscalers, two different jobs. Pods scale inside a node (HPA, based on CPU utilization of requests); nodes scale inside the account (Karpenter, based on pods that cannot be scheduled). Confusing them is the classic mistake; the whole of Chapter 6 exists to keep them straight.

1-5.Tenancy is a platform responsibility. When many things share one cluster, the person running the cluster owns the boundaries: what each tenant may consume (quota, limits) and what each tenant may reach (network policy). That is the entire job of a platform team, compressed into Chapter 5.

Note — ephemeral by design

Every choice in this architecture (code, not clicks; git, not state; teardown, not goodbye) exists so the platform can be born, studied, and destroyed in a month. If a component can only be built but not torn down, it does not belong in the exercise.

Chapter 2 — System architecture & the life of a deployment

2-1.The path from a commit to a live URL. Follow one change through the whole system — this is the picture the project exists to make you hold in your head:

  1. You push a change to an app in GitHub. This is the only human action in the loop.
  2. GitHub Actions builds the container image and runs a minimal check. It authenticates to AWS by federation (OIDC) — it is trusted temporarily, with no stored keys.
  3. The image lands in ECR under an immutable tag: the commit SHA. The tag is the version's identity for life.
  4. Actions updates the manifest in the gitops/ repository — the desired state now points at the new tag.
  5. ArgoCD notices the drift between the gitops repo and the live cluster, and syncs: it applies the manifest, creating or updating the namespace, quota, deployment, service, ingress, and HPA for that app.
  6. The scheduler places the pods on nodes. If no node has room, Karpenter provisions one.
  7. The ingress controller routes app.<domain> through the ALB to the app's Service, which load-balances to the pods.
  8. Prometheus scrapes metrics; if the app's CPU crosses the HPA target, replicas grow — and if pods no longer fit, Karpenter adds a node. Grafana shows all of it.

3-1.The division is deliberate: infra/ is the "born once" layer, gitops/ is the "runs forever" layer, and apps/ is the layer your pushes touch daily. Knowing which file answers which question ("how is the cluster made?" → infra/; "what is running and why?" → gitops/) is half of operating the system.

Chapter 4 — The components, one by one

Component anatomy
Amazon EKS
The managed control plane. AWS runs the API server and etcd for you; you pay a flat hourly rate and operate only the worker nodes. Kubernetes knowledge transfers directly — EKS is stock Kubernetes, not a fork.
Karpenter
The node autoscaler. It watches for unschedulable pods, picks the cheapest instance type that fits, provisions it, and later consolidates idle nodes away. It is the reason "the cluster grows when the platform needs it".
ArgoCD
The GitOps controller and therefore the deployment engine. Declarative, self-healing, prunes anything git removed. Its "Application" is the unit of deployment — one per tenant.
AWS Load Balancer Controller
Turns a Kubernetes Ingress object into a real ALB and wires the target group to your Services. The bridge between Kubernetes routing and AWS networking.
kube-prometheus-stack
A Helm chart bundling Prometheus (metrics storage + scraping), Grafana (dashboards), node-exporter (node metrics), and kube-state-metrics (cluster object metrics). Installed in one command; the whole observability story.
IRSA
IAM Roles for Service Accounts: a Kubernetes ServiceAccount maps to an IAM role, and pods assume that role via projected credentials. No access keys inside the cluster, ever.
GitHub OIDC
The CI job presents a signed token to AWS; AWS verifies it and mints short-lived credentials. The pipeline is trusted for a few minutes per run instead of holding keys forever.
Terraform state
S3 bucket (state file) + DynamoDB (lock). The ledger that makes plan/apply and destroy possible — and the thing that makes the whole project disposable.

Chapter 5 — Multi-tenancy & isolation explained

5-1.A platform's job is to let many things share one cluster without hurting each other. Three mechanisms compose to do that, and they are deliberately separate:

MechanismAnswersEnforced by
Namespace"What is mine?" — a named boundary for objectsAPI server
ResourceQuota + LimitRange"How much may I take?" — totals per namespace, per-pod boundsAdmission control (rejects before a pod exists)
NetworkPolicy"Who may I talk to?" — default-deny, allow same-namespace, allow ingressCNI (enforced on the data path)

5-2.Why all three? Because each answers a different question and they fail independently. A namespace without a quota lets one tenant starve the cluster; a quota without a network policy lets one tenant reach another's data. This is also exactly how a production platform team thinks — the demo apps are stand-ins for real tenants, but the controls are the real thing.

5-3.A subtlety worth naming: quota rejection happens at admission time and surfaces as an event, not a container log. Learning to read events (kubectl describe, kubectl get events) rather than only logs is one of the quiet skills this project teaches.

Chapter 6 — Autoscaling economics

6-1.HPA is the pod dial. The HorizontalPodAutoscaler watches the CPU utilization of the requests (not the machine's CPU). Because the demo apps request 50m CPU and HPA targets 50%, a modest load crosses the threshold quickly — the demo is tuned so the lesson fires with light effort. What HPA cannot do is create more machine.

6-2.Karpenter is the machine dial. When pods exist that no current node can fit, Karpenter buys a node; when nodes sit idle past the consolidation window, it sells them back. Node choice is a cost-and-speed dial: t3.medium was chosen because it is the smallest instance where a handful of extra replicas actually forces a new node — the node-scaling lesson cannot even be observed on a bigger instance.

6-3.The cost picture. The EKS control plane costs the same whether nodes are micro or medium — that is why "use a smaller instance to save money" is a trap (TM-001 Appendix B). Real levers: node count, spot vs on-demand, and NAT choice.

Note — downscaling is half the lesson

Everyone demonstrates scale-up. This project deliberately demonstrates scale-down too: stop the load, and both HPA and Karpenter must consolidate back to baseline. A platform that only grows is a platform that only bills.

Chapter 7 — CI/CD: how code becomes a running platform

7-1.CI (Continuous Integration) is the build side: every push is compiled, checked, and containerized in a reproducible way. CD (Continuous Delivery) is the release side: the artifact is delivered and promoted. In this platform, CI lives in GitHub Actions and CD is GitOps — the delivery mechanism is a git commit that a controller reconciles. There is no SSH-into-a-server-and-restart anywhere in the loop.

7-2.Why OIDC and not keys? A stored AWS access key is a permanent credential that outlives its usefulness and leaks. OIDC federation replaces it with a trust relationship: the pipeline proves its identity to AWS with a short-lived signed token, gets short-lived credentials, and is done. It is both more secure and simpler to operate — no secret rotation, no "where did the key go".

7-3.Why immutable tags? The image is tagged with its commit SHA, so a running version can always be traced back to the exact code that produced it. It also makes rollback trivial: point the manifest at the previous tag (via git revert) and sync. The tag, the git history, and the running pod must always tell the same story — if they ever disagree, someone bypassed the loop.
